# 案例：有評估的法規語意搜尋

> 用自然語言找出相關的法規條文與施工規範章節。在**架構定案後才寫、只跑一次**的保留測試集上，
> Recall@5 從原本字詞搜尋的 **0.54 提升到 0.91**；
> 過程中評估推翻了第一版設計：「字詞相似度＋向量」的混合**反而輸給純向量**，拿掉字詞那一路才是對的。

程式：`backend/app/search/`（`corpus.py`、`embeddings.py`、`hybrid.py`）、
`backend/app/services/knowledge_search_service.py`、`GET /api/search/knowledge`。
評估：`scripts/eval_search.py`、`data/search_eval/`，完整數字在 [search-eval-results.md](search-eval-results.md)。

---

## 1. 問題

監造與品管人員常常知道「要找什麼」，卻不知道「它寫在哪一條」：

- 「溝挖到一米五以上要不要做支撐？」——答案是營造安全衛生設施標準第 71 條，條文寫的是「露天開挖」「擋土支撐」。
- 「包商可以把整個工程丟給別家做嗎？」——政府採購法第 65 條，條文寫的是「轉包」。

原本的「搜尋」分頁是字元雙字組 TF-IDF，只比字面。上面兩題的字面重疊很少，找不到。
但也有另一種查詢：「營造安全衛生設施標準第 19 條」「03310」「CNS 14253」，使用者要的是**那一條**，
不需要語意，需要精確。

## 2. 架構取捨

**向量存在既有的 PostgreSQL（pgvector），不另外架向量資料庫。** 原本的開發計畫寫的是 Phase 2 上 Qdrant，這次改掉了：

| | pgvector | 獨立向量資料庫（Qdrant 等） |
|---|---|---|
| 規模 | 語料 2,704 筆，PostgreSQL 綽綽有餘 | 為百萬筆以上設計，這裡用不到 |
| 一致性 | 條文和法規主檔在同一個資料庫，一個交易、一套備份與權限 | 兩邊要同步，多一個會壞的地方 |
| 查詢 | 搜尋結果要對法規主檔的現行／廢止狀態，同一個資料庫 join 就好 | 要跨系統組合 |
| 部署 | docker-compose 的 `postgres:15` 換成 `pgvector/pgvector:pg15`，其他不變 | 多一個服務要監控 |

什麼時候該換：語料到數百萬筆、或需要向量專用的分散式擴充時。換的成本也低：
向量那一路只在 `KnowledgeSearchService._vector()` 一個函式裡。

**Embedding 用本機開源模型（`BAAI/bge-m3`），不呼叫外部 API。** Anthropic 沒有 embedding API；
更重要的是使用者上傳的工程文件不一定能送出去，而且評估要能重現。代價是 CPU 上查詢向量化約 110 ms，
以及 torch 很大，所以放在選用的 `requirements-semantic.txt`。預設 `EMBEDDING_PROVIDER=none`，
沒裝模型時搜尋退回條號比對＋字詞相似度，畫面會說明，測試與 CI 都不需要 torch。

**語料只收確定需要的**（`data/search_corpus.json`）：工程品管、施工安全、採購與建築管理常用的 27 部法規
（全國法規資料庫，2,389 條條文），加上施工綱要規範 315 章（工程會目錄，只有章名），共 2,704 筆。
不是把一萬多部法規全倒進來：無關的法規只會增加干擾。內文只剩「（刪除）」「〈移至建築構造編〉」的
523 筆佔位條文也不收，它們很短，對短查詢反而語意相近，會擠進搜尋結果。

## 3. 評估方法

先有評估，再談改進。

**題目**：開發集 55 題、保留測試集 32 題，分三類：

| 類型 | 例子 | 測什麼 |
|---|---|---|
| 指名條號／章碼／標準 | 「採購法第二十二條」「規範第02742章」「CNS 4750 施工架」 | 精確比對 |
| 關鍵字 | 「押標金 發還」「施工架組配作業主管」 | 用條文裡的術語 |
| 口語描述 | 「挖地下室把隔壁房子弄歪了，事前應該做什麼」 | 刻意避開條文字眼 |

**標註**：題目先依工程實務寫好，再到條文全文裡逐條確認答案，沒有參考任何一種搜尋方法的結果。
一題可以有多個正確答案（例如「轉包」→ 政府採購法第 65、66 條）。

**開發集與測試集分開**：開發集的結果我看過，也拿來決定架構。只用開發集報數字，等於拿考題練習。
保留測試集是架構定案後才寫的，寫好只跑一次，之後不再依它調整搜尋方法。標題的 0.54 → 0.91 是測試集的數字。

> 透明起見：測試集跑過之後，在畫面上發現上面說的 523 筆「（刪除）」佔位條文，濾掉後兩份評估集都重跑了一次。
> 這是資料清理、不是依測試結果改方法，而且採用方案的數字沒有變（開發集 0.89、測試集 0.91）；
> 變的是字詞搜尋這條基準線（開發集 0.47 → 0.51），以下表格都是清理後的數字。

**指標**：Recall@5（正確答案有幾成在前 5 名）、Hit@1、MRR@10。前 5 名是一個人實際會看的範圍。

**不調參數**：RRF 的 k=60 是原論文的值；候選數 50 是固定值。題目只有幾十題，在上面調權重沒有意義。

## 4. 結果：評估推翻了第一版

第一版設計是業界常見的三路混合：**精確比對 ＋ RRF(字詞相似度, 向量)**。開發集（bge-m3）：

| 方法 | Recall@5 | 指名條號 | 關鍵字 | 口語描述 |
|---|---:|---:|---:|---:|
| 字詞相似度（原本的搜尋） | 0.51 | 0.36 | 0.86 | 0.41 |
| 純向量 | **0.80** | 0.64 | 0.96 | **0.80** |
| 精確比對＋RRF(字詞, 向量)（第一版） | 0.76 | **1.00** | 0.89 | 0.57 |

混合在「指名條號」那類完勝（1.00 對 0.64，向量模型分不出第 19 條和第 91 條），
但**整體輸給純向量**：口語題從 0.80 掉到 0.57。原因是 RRF 只看名次，把兩路當成一樣可信；
字詞那一路在口語題上幾乎都排錯，合併後把向量排對的答案往下擠。

逐題看就很清楚：「溝挖到一米五以上要不要做支撐」，向量第 1 名就是第 71 條；
字詞那一路把一堆有「挖」「支撐」字樣的隧道條文排在前面，合併後第 71 條掉出前 5 名。

所以第二版**拿掉字詞相似度，只留精確比對＋向量**。這其實才是「混合」原本的意思：
關鍵字負責**要精確比對的東西**（條號、章碼、標準編號），向量負責語意。字詞相似度只在語意模型沒有啟用時當備援。

| 方法（bge-m3） | 開發集 Recall@5 | **保留測試集 Recall@5** | 測試集 Hit@1 | 測試集 MRR@10 |
|---|---:|---:|---:|---:|
| 字詞相似度（原本的搜尋） | 0.51 | **0.54** | 0.41 | 0.46 |
| 純向量 | 0.80 | 0.80 | 0.56 | 0.66 |
| 精確比對＋RRF(字詞, 向量)（第一版） | 0.76 | 0.83 | 0.62 | 0.72 |
| **精確比對＋向量（採用）** | 0.89 | **0.91** | 0.72 | 0.80 |

測試集的數字和開發集一致，代表這個決定不是過度擬合開發集。

### 模型夠強，才不需要字詞那一路

同樣的評估換成小模型 `paraphrase-multilingual-MiniLM-L12-v2`（384 維，查詢 12 ms），結論**反過來**：

| 方法（MiniLM） | 開發集 | 保留測試集 |
|---|---:|---:|
| 純向量 | 0.30 | 0.33 |
| 精確比對＋RRF(字詞, 向量) | **0.56** | **0.62** |
| 精確比對＋向量 | 0.52 | 0.55 |

小模型的中文語意能力不足，純向量甚至輸給字詞相似度（0.30 對 0.51），這時字詞那一路是在補模型的洞。
**要不要合併字詞相似度，取決於 embedding 模型夠不夠強**，沒有放諸四海皆準的答案。只看文章說「混合比較好」就照做，
在這裡會選錯。換模型時要重跑 `scripts/eval_search.py`。

## 5. pgvector 的實際陷阱

PostgreSQL 版的結果要和評估（記憶體計算）一致，評估數字才代表上線的行為。驗證時遇到兩個坑：

1. **多一個排序鍵，索引就用不上。** 原本寫 `ORDER BY embedding <=> :q, ref`（加 `ref` 讓同分時結果穩定），
   HNSW 索引只能處理「只依距離排序」，結果變成全表算距離再排序。
2. **HNSW 一次最多回傳 `hnsw.ef_search` 筆（預設 40）。** 候選要取 50 筆，強制走索引時只拿到 40 筆，
   而且不會報錯。查詢前 `SET LOCAL hnsw.ef_search = 100`。
3. **整批重建後沒有統計資料，規劃器會選錯。** 重建完馬上查，規劃器改走近似的 HNSW，87 題裡有 7 題前 5 名和評估不同；
   `ANALYZE` 之後才回到精確的全表掃描。`rebuild()` 現在寫完就 `ANALYZE`。

修正後，87 題（兩份評估集）的比對結果：

| 執行方式 | 前 5 名和記憶體版完全相同 | Recall@5 |
|---|---:|---:|
| 記憶體精確計算（評估腳本） | — | 0.897 |
| PostgreSQL，規劃器自選（2,704 筆時選全表掃描，等於精確） | 87 / 87 | 0.897 |
| PostgreSQL，強制走 HNSW（近似） | 80 / 87 | 0.885～0.897（每次建索引不同） |

2,704 筆全表掃描只要 13 ms，規劃器不會選 HNSW；語料變大後它會自動切換，
那時的代價就是上表最後一列：少數題目名次變動，Recall 最多掉約 1 個百分點。

## 6. 還沒做、做不好的

- **題目是自己出、自己標的。** 雖然先寫題目再找答案、測試集定案後只跑一次，仍然可能偏向「我想得到的問法」。
  真正的使用者查詢紀錄到手後，應該用那些重新評估。
- **規模小。** 87 題的 Recall@5 差 0.05 大約是 2～4 題，表裡的小差距不要過度解讀；0.54 → 0.91 這種差距才確定。
- **規範章節只有章名**，沒有內文。「混凝土澆完之後要怎麼保濕」找不到 03390 混凝土養護，因為只有「養護」兩個字可以比。
- **還沒有重排序（reranker）。** 混合搜尋沒找齊的 11 題（開發 7、測試 4）裡，漏掉的正解大多排在第 8～19 名
  （只有「施工日誌」和「樓板洞口」各有一個正解掉出前 50 名），在候選範圍內但排不上來。
  cross-encoder 重排序前 50 名是下一步，評估腳本可以直接比較。
- **文件段落搜尋仍是字詞相似度。** 這次只做法規條文與規範章節；使用者上傳文件的段落要即時建向量，另外處理。

## 7. 重現

```bash
pip install -r requirements-semantic.txt
python scripts/sync_taiwan_law.py --keep-raw     # 條文全文（data/taiwan_law_cache/）
python scripts/sync_pcces.py                     # 施工綱要規範目錄
python scripts/eval_search.py --models BAAI/bge-m3 sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 --misses
```

第一次跑要下載模型、對 2,704 筆算向量（bge-m3 在 CPU 上十幾分鐘），向量會快取在 `data/generated/embeddings/`，
之後幾十秒跑完。上線用：

```bash
EMBEDDING_PROVIDER=local python scripts/build_search_index.py   # 寫進 knowledge_chunks（PostgreSQL 存成 pgvector）
```

後端以 `EMBEDDING_PROVIDER=local` 啟動，「搜尋」分頁就會用混合搜尋；畫面上每筆結果都標出是「指名條號」還是「語意第幾名」命中的。
