## 既有程式的接點與缺口

- `DocumentRole.DRAWING` 已存在，但沒有圖說索引、圖項來源證據、圖項人工覆核或工項聯集流程。
- `ProjectService.build_work_items` 目前只讀第一份標單，重建時刪除舊工項。新增圖說關聯後，必須設計失效與重建規則，避免舊關聯掛到已刪除的工項。
- `PdfParser` 對全掃描 PDF 報錯，不能直接處理結構圖。
- `MAX_UPLOAD_SIZE_MB` 與 nginx 均為 50 MiB，建築圖無法上傳。API 目前一次 `file.read()` 讀完整檔案；支援大型圖檔時應改為有界分段寫入與雜湊，並在超限或失敗時清理暫存檔。
- 前端 `UploadPanel` 仍限制 DOCX/PDF/TXT，與後端已接受 Excel 的設定不一致；階段 2 入口要同步修正。
- 現有檢核表的 `OK` 只描述施工規範依據，不包含圖說一致性。兩種檢核結果應分欄顯示，避免改變原有 `OK` 的語意。

## 建議實作範圍

### 1. 圖說索引與來源證據

每筆圖說保留專案、文件、實體頁碼、圖號、圖名、原文及解析方式。

先解析有文字層 PDF 的標題欄與索引表，以座標分欄／分列；索引列需驗證是否有相應圖頁，不把目錄中的每個圖號直接視為已收到該張圖。

圖框解析不可靠、同一圖號出現多個版本、缺圖名或疑似掃描頁時，保留待確認狀態。所有掛在專案下的圖說文件都要處理，不能只取第一份。

### 2. 掃描圖處理

結構圖需要新增 OCR 能力，這超出原設計「不支援掃描 PDF」的範圍。

建議先以本機 OCR 處理圖框及目錄，保存原始辨識文字與人工修正值。先用少量頁驗證方向、圖號字母／數字及中文圖名，再考慮全檔；目前尚未選定或驗證 OCR 引擎。

如果暫不加入 OCR，必須提供人工登錄圖號、圖名、頁碼的入口，並清楚顯示尚未讀取的頁數。不能把「解析失敗」存成「沒有圖項」。

### 3. 圖項與標單聯集

圖名不是標單明細工項。不能把「三至六層平面圖」直接當成一個施工工項，也不能把章節代碼視為同一筆標單明細的唯一鍵。

- 由圖名與圖中文字產生圖項候選，保留所在圖頁與原文。
- 明確項次／代碼可提供精確關聯；一般名稱比對只提供候選，通用詞與模糊字串不得直接確定配對。
- 人工可確認、拒絕或補上圖項與標單關聯；支援一個工項多張圖、一張圖多個工項。
- 聯集包含標單項目及已確認的圖說獨有項目，圖說獨有項目不可捏造標單項次、數量、單位或計價代碼。

### 4. 差異狀態與畫面

圖說檢核獨立顯示：

- 已找到圖說依據。
- 尚未找到圖說依據，待人工確認。
- 圖說提出、尚未找到標單對應。
- 圖面尚未讀取／解析不完整。

只有在使用者確認圖說集合完整、解析／人工覆核足夠，且完成差異確認後，才能顯示確定的「標單有，契約圖沒有」。單靠搜尋不到不能推出不存在。

每筆候選都可回到圖檔頁碼與圖號，並呈現原設計要求的人工判定尾註。原有施工規範檢核與單份文件分析流程保留。

## 驗證要求

1. 合成 PDF 測試：多欄目錄、標題欄、旋轉頁、無文字頁、多圖號及重複版本。
2. 關聯測試：一對多、多對一、拒絕候選、同名不同明細、圖說獨有項目與解析不完整時禁止肯定缺漏。
3. 資料庫與 API 測試：不同專案隔離、重建去重、標單重建後關聯失效、失敗時保留前次有效資料。
4. 前端測試：圖說來源、待確認狀態、覆核操作、跨專案切換及錯誤顯示。
5. 大型上傳測試：後端與代理上限一致、超限及中斷不殘留檔案、不將整檔讀進記憶體。
6. 真實圖檔驗證分開報告文字層與 OCR 結果，不把抽樣頁可讀推論成全檔可靠。
7. 收到同案標單後，才做真實工項差異驗收；舊文件的 1,028 筆範例不能直接套到本案。
