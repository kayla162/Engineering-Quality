# 工項檢核表（綠框整合）設計

日期：2026-09-11
狀態：待審閱

---

## 1. 要解決的問題

品管人員目前的工作方式（來源：使用者提供的 `邏輯.docx` 流程圖）：

```
綠框（一切的依據）
├─ 契約及契約圖   最高位階，只能優於法規
├─ 法規           注意雙重規範
└─ 施工規範       工程會／地方工務局／契約附件，材料到工法都涉及
                    │
                    ▼  「原本要每個工項都去翻綠框那幾個去核對」
                  品管人員逐工項人工整合
                    │
                    ▼
橘框（產出）
├─ 承攬廠商：檢查標準表、自主檢查表、施工流程圖、施工要領
└─ 監造單位：材料抽驗標準表、施工抽查標準表、施工抽查紀錄表
```

**要自動化的是中間那一步**——把綠框依工項整合起來，產出一張初步檢核表。

系統目前的限制：一次只分析一份文件，沒有「專案」概念，也沒有「工項」概念。

## 2. 產出物

一張以**工項為列**的檢核表：

| 工程項目 | 檢核結果 | 工法 | 契約 | 契約圖 | 法規 | 施工規範 |
|---|---|---|---|---|---|---|
| 假設工程 | OK | — | 第○條 | 圖 A-01 | 營造安全衛生設施標準 | 01510 臨時設施 |
| 開挖工程 | 請檢討使用何種工法 | 未指定（相關圖號 S-12、S-13） | 第○條 | 圖 S-12 | … | 02300 土方工作 |
| 空調工程 | 標單有，契約圖沒有 | — | 第○條 | **✗** | … | … |

表尾固定印出：

> ※ 以上為 AI 初步檢核結果，實際仍須依品管人員為主

這句話**不是可選項**。系統定位是初篩，不是拍板；少了它，這張表會被當成結論用。

## 3. 範圍

### 做

- 專案層級：一個專案多份文件，每份文件有角色
- 工項清單：由標單詳細表與契約圖取**聯集**
- 四個綠框來源各自比對到工項，找出依據
- 檢核結果與工法欄的判定
- 匯出（沿用現有的 XLSX／CSV／PDF 管線）

### 不做（明確排除，避免無限膨脹）

- **不產出橘框文件的完整草稿**。產出的是檢核表，不是品質管理標準表。
- **不判讀圖面內容**。只列圖號，讓人去看圖判斷——理由見第 7 節。
- **不做承攬廠商 vs 監造單位的跨計畫勾稽**。流程圖上有這條線，但那是另一個題目。
- **不檢查橘框文件的內容是否符合綠框**。那是再下一層。
- **不支援掃描版 PDF**（沿用現有限制，需要 OCR）。

## 4. 資料模型

新增四個概念。現有的 `documents` / `regulation_references` 不改語意，只多掛一層專案。

```
Project                 專案
  └─ ProjectDocument    文件 + 角色（標單／契約／契約圖／施工規範）
        └─ Document     沿用現有的 documents，解析與抽取流程完全不變

WorkItem                工項（專案層級）
  ├─ name               「開挖工程」
  ├─ sources            來自標單／契約圖／兩者
  ├─ method_required    這個工項要不要選工法
  ├─ method             選定的工法（可為空）
  └─ WorkItemBasis[]    每個綠框來源對這個工項的依據
        ├─ source_role  契約／契約圖／法規／施工規範
        ├─ reference    指向既有的 regulation_references 或圖號／條號
        └─ found        有沒有找到
```

`WorkItemBasis.found` 是檢核結果的計算基礎，不是另外存一份判斷——**狀態由資料算出來，不要存成可能過期的欄位**（與 `regulation_references.status` 的既有作法一致）。

## 5. 工項清單怎麼建立

> 2026-09-17 更新：拿到真實標單（`2.契約書.xls`）與契約書（`1.契約書.pdf`）驗證後改寫。
> 原本假設工項要靠名稱模糊比對；實際上標單裡有兩個可以精確對接的代碼。

### 5.1 標單的實際結構

真實標單是 **OLE2 格式的 `.xls`**，四張工作表：

| 工作表 | 列數 | 內容 |
|---|---|---|
| 契約總表 | 71 | 項次階層與金額 |
| **契約詳細表** | 2669 | `項次 / 項目及說明 / 單位 / 數量 / 單價 / 複價 / 編碼(備註)` |
| 契約單價分析表 | 3175 | 每個工項的工料拆解 |
| 契約資源統計表 | 1364 | `工項代碼 / 工項名稱 / 單位 / 用量…` |

工項清單取自**契約詳細表**。

### 5.2 項次是精確的 join key，不要用名稱模糊比對

詳細表的項次是階層碼：`壹` → `壹.一` → `壹.一.1` → `壹.一.1.1.1`。

同樣的項次也出現在品質計畫書裡（真實文件已驗證：`壹.一.1.4.7`、`壹.一.1.6.8`）。所以**標單與品質計畫的工項可以用項次精確對接**，名稱模糊比對只當後備。

### 5.3 計價代碼直接對到施工綱要規範章節

「編碼(備註)」欄的 10 碼計價代碼，**前 5 碼就是施工綱要規範的章碼**。實測：

```
0172500004  ->  第01725章 施工測量        | 標單：施工測量，基地測量及鑑界費
0152300004  ->  第01523章 施工安全衛生及管理 | 標單：施工安全衛生及管理，安全警示…
0311010002  ->  第03110章 場鑄結構混凝土用模板 | 標單：普通模板，普通模板含組立…
```

實測（2026-09-17，用真正的標單讀取器重算；先前 spec 寫的 63% 是一次性掃描的錯誤分母，已作廢）：

| | 筆數 | 佔比 |
|---|---|---|
| 工項總數 | 1028 | |
| 其中有計價代碼 | 513 | 50% |
| 代碼對到綱要規範章節 | 438 | **佔有代碼者 85%／佔全部工項 43%** |

兩個數字要分開講，混在一起會誤導：**有代碼的話，對到章節的機率很高（85%）；但只有一半的工項有代碼。**

對不到的多半是各機關自訂的專業工項（16xxx 電氣 32 筆、09xxx 裝修 15 筆、11xxx 設備 8 筆…），不在 `pcces` 同步的「共通性工項」315 章裡。

**影響**：檢核表的「施工規範」欄約四成可以**決定性**填入，不是猜的。另外五成的工項連代碼都沒有，只能走名稱比對，而且要明確標示信心較低。

### 5.4 工項來源與優先序

兩個來源取聯集，不一致本身就是檢核發現：

- 標單有、契約圖沒有 → `標單有，契約圖沒有`
- 契約圖有、標單沒有 → `契約圖有，標單沒有`（使用者原話：「可能發生 2.有 1.沒有」）

**契約本身已經規定了誰優先**（`1.契約書.pdf` 第 1 頁，契約文件優先順序第八款）：

> 招標文件內之標價清單，其品項名稱、規格、數量，優於招標文件內其他文件之內容。

所以不一致時，**標單的品項名稱、規格、數量為準**，檢核表要把這條依據一起印出來——讓人知道這不是系統的判斷，是契約寫的。

## 6. 檢核結果

| 值 | 條件 |
|---|---|
| `OK` | 四個綠框來源都找到依據，且工法欄沒有懸而未決 |
| `請確認依據` | 有來源找不到依據。**刻意不說「缺少依據」**——分不出是真的缺、還是系統沒找到 |
| `標單有，契約圖沒有` | 工項來源不一致 |
| `請檢討使用何種工法` | 需要選工法，但找不到選了哪一種 |

多個條件同時成立時，依「工項來源不一致 > 工法未定 > 依據不全 > OK」的順序取最需要人介入的那一個，並在明細列出全部。

## 7. 工法欄

使用者的說明（原話）：

> 施工規範有些會寫多種工法供選擇
> 1. 主要從契約圖抓，但建築師不一定有文字說明，可能可以讓 AI 列出「圖說有相關的圖號」，
>    因為圖面 AI 可能無法判斷？讓人工去判斷是何種工法
> 2. 有些契約可能會有附件比如需求書之類的，會文字提到，但不一定有

拆成兩個獨立判斷：

**這個工項要不要選工法** → 施工規範裡同一類工作列出多種工法時，就是要選。

**選了哪一種** → 依序：

1. 契約附件（需求書等）的**文字**有寫 → 直接填
2. 否則 → **不猜**，填 `未指定`，並列出相關圖號

第 2 點是這個設計最重要的一條線。圖面內容系統讀不懂，硬猜出來的工法會是「有信心的錯」——和先前 CNS 標準被判成施工綱要規範章節同一類的錯誤，而且更難被發現。所以輸出長這樣：

```
請檢討使用何種工法（相關圖號：S-12、S-13）
```

圖號比一句空泛的提示有用得多：它直接告訴人要翻哪一張圖。

## 8. 風險與待驗證

| 風險 | 狀態 | 影響 / 處理 |
|---|---|---|
| **系統完全不接受 Excel** | 🔴 **已確認，是阻斷項** | `ALLOWED_EXTENSIONS` 只有 `.docx,.pdf,.txt`，`parsers/` 沒有 Excel 解析器。而真實標單是 **OLE2 格式的 `.xls`**（不是 `.xlsx`，openpyxl 讀不了，要 `xlrd`）。**沒有這個解析器，整個設計的入口就不成立**——必須排在第 1 階段第一件事 |
| 契約書 PDF 能不能解析 | 🟢 **已驗證可行** | 用專案自己的 `PdfParser` 跑真實契約書：130 頁、2297 段，文字可選取 |
| **契約圖多半是掃描或 CAD 匯出的 PDF** | 🟡 **仍未驗證** | 使用者提供的是契約「書」，不是契約「圖」。抽不到文字的話，第 7 節的圖號功能整個不成立，設計要重做。動工到第 4 階段前必須先拿一份真實契約圖驗證 |
| 圖號與工項的關聯靠圖名模糊比對 | 🟡 未驗證 | 對錯圖號比沒有圖號更糟。比對不到就留空，不要給低信心的圖號 |
| 標單格式各家不同 | 🟡 只驗過一份 | 這份的工作表叫「契約詳細表」、表頭在第 6 列。欄位要用表頭文字定位，不能寫死列號；找不到表頭要報錯，不是產出空表 |
| 只有一半工項有計價代碼 | 🟢 已量測 | 1028 個工項裡 513 個有代碼，其中 85% 對得到章節（全部工項的 43%）。**沒有代碼的那五成**只能走名稱比對，要標示為低信心，不要混在決定性結果裡 |

**第一項是阻斷項**，在寫任何檢核邏輯之前要先解決。

## 9. 分階段

| 階段 | 內容 | 可獨立驗證的價值 |
|---|---|---|
| **0** | **Excel（`.xls` / `.xlsx`）解析器** + 開放副檔名 | 標單進得來。沒有這個後面全部不成立 |
| 1 | 專案 + 多文件角色 + 從標單建立工項清單（項次階層 + 計價代碼） | 能看到完整工項清單，約四成已對到綱要規範章節 |
| 2 | 契約圖工項 + 聯集 + `標單有，契約圖沒有` | 第一個真正的檢核發現 |
| 3 | 四個綠框來源的依據比對 + `OK` / `請確認依據` | 主要價值落地 |
| 4 | 工法欄 + 圖號 | 需要第 8 節的驗證先過 |

每個階段都要有自己的 golden set 案例，沿用 `backend/tests/golden/` 既有機制。

## 10. 與現有功能的關係

- 單份文件的分析流程**不變**。專案是加在上面的一層，不是取代。
- 目前 golden set 裡 5 筆「承攬廠商自有文件」亂抽（品質管理標準、作業標準…），在這個設計下會被歸位成橘框，而不是繼續當法規引用硬擋。
- 免責尾註要同時出現在畫面與三種匯出格式。
