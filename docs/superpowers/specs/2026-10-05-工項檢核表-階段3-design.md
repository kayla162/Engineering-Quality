# 階段 3：綠框依據比對設計

日期：2026-10-05
狀態：待審閱
延續：`docs/superpowers/specs/2026-09-11-工項檢核表-design.md`（以下稱「原 spec」）

---

## 1. 這一階段做什麼

原 spec 第 9 節把階段 3 定為「四個綠框來源的依據比對 + `OK` / `請確認依據`」，
並標註為「主要價值落地」。

階段 1 已經做出工項清單（1028 個工項，438 個對到施工綱要規範章節）。這一階段
回答下一個問題：**每個工項的依據在哪裡**。

階段 2（契約圖工項聯集）**跳過**——使用者手上沒有契約圖，那個階段不是難做，
是輸入不存在。拿到圖之後再回頭補，接點是 `WorkItem.item_no`（原 spec 5.2 節）。

## 2. 實際覆蓋率（先講，因為它決定這張表值不值得做）

用真實標單（1028 個工項）與真實施工規範（`13.施工規範.pdf`，772 頁、86 章）實測。
下面是實作完成後（2026-10-07）重測的值，也是第 8 節的驗收基準；設計初稿的預估是
590 / 250 / 235 / 15（請確認依據占 59%），已被這組實測值取代：

```
工項總數                                   1028
├─ 沒有計價代碼或對不到章節  → 請確認依據      589  (57%)
├─ 有章節但本案規範未收錄    → 本案規範未收錄   188  (18%)
└─ 章節在本案規範書裡                         251  (24%)
    ├─ 該章有相關準則／標準 → OK               248  (24%)
    └─ 該章沒有            → 請確認依據           3
```

「請確認依據」合計 **592 筆（58%）**，由三種原因組成：515 筆沒有計價代碼；74 筆有代碼，
但章碼既不在本案規範書、也不是施工綱要規範的任何一章（17 個章碼）；3 筆的章在本案規範書
裡，但這一章沒有宣告可抽出的依據。前兩種合計 589，就是上圖第一行。

**這張檢核表會有 58% 是「請確認依據」。** 這是「只給確定的依據」這個前提的直接
後果，不是估計值。沒有計價代碼、或代碼不是任何一章的那 589 筆就是查不到，硬填就是造假。

仍然值得做的三個理由：

1. **248 筆真的被自動化了**——它們會拿到該章節「相關準則」列出的法規與標準（有這一段的
   79 章裡，75 章編在 `1.4`、4 章編在 `1.3`），那正是原 spec 第 1 節說要取代的「逐工項去翻
   綠框」。
2. **188 筆是全新的檢核發現，但要先分流，不是 188 個漏洞**——「標單用到這一章，但本案
   施工規範沒收錄」。實作完成後（2026-10-07）依章拆開實測：這 188 筆分屬 26 章，單一
   最大的是 `01271` 計量與計價，**83 筆，佔 44%**；其次是 `13706` 門禁管制設備（21）、
   `02891` 標誌（11）、`01450` 品質管理（10）、`10801` 浴廁附屬配件（9）、`13100`
   避雷設備（9），其餘 20 章合計 45 筆。計量與計價、品質管理是行政、管理性質的章，施工
   規範本來就可能不收，不一定是漏收（兩章合計 93 筆，佔 49%）；門禁管制設備、避雷設備
   這類章對應標單裡真要施作的工項，規範書沒收錄才是實質的缺漏。所以這個發現的價值是
   「指出哪幾章要人去判斷」，不是「規範書漏了 188 項」；系統不區分章的性質，分流要由人
   做。這個發現目前沒有任何人在做，原 spec 也沒有預料到。
   （本節初稿把「數據網路交換處理設備（14）」也列為例子；實測它不在這 188 筆裡——
   `16742` 章在本案規範書裡，那 14 筆是 `OK`。）
3. **592 筆被誠實標記**。對照組：用工項名稱比對契約，表面覆蓋率 61%，但其中 93%
   來自「產品」（517 個工項）與「施工費」（70 個）這兩個通用前綴——填滿的欄位比
   空白的欄位更難發現是錯的。

## 3. 對原 spec 的三處修正

實測之後有三件事和原 spec 的假設不同。

### 3.1 契約欄不做逐工項比對

原 spec 第 2 節的產出物表格有「契約」欄，範例填「第○條」。實測否定了這個做法：

- 工項名稱的首段詞在契約書裡找得到的有 630 個（61%），但 **587 個來自「產品」與
  「施工費」兩個通用前綴**，真正有意義的命中約 43 個（4%）。
- 契約書裡 `第N條` 出現 143 次、68 個相異值，但多數是在**引用政府採購法**的條文，
  不是契約自己的條次。契約自己用「一、二、三」編號，頁首寫的是「工程契約第九條」。

台灣公共工程契約是**管整個案子**的，不是逐工項的。所以：

契約欄改為**專案層級**：檢核表表頭印出契約文件優先順序那一條（原 spec 5.4 節
已引用），說明不一致時以標單的品項名稱、規格、數量為準。

逐列**不出現**契約依據。階段 3 不做任何工項到契約條文的連結——沒有可靠的連結方式，
做一半會留下一個半滿的欄位，比沒有更難判讀。

### 3.2 新增檢核結果值 `本案規範未收錄`

原 spec 第 6 節有四個值。實測發現第五種狀況：工項對得到 PCCES 章節，但那一章
不在本案施工規範書裡（188 筆，18%）。

這和「沒有計價代碼所以不知道」是**完全不同的狀況**——這裡是「知道該用哪一章，
但合約文件裡找不到它」。混進「請確認依據」會把訊息埋掉。

| 值 | 條件 | 階段 3 可達 |
|---|---|---|
| `OK` | 章節在本案規範書裡，且該章有相關準則／標準 | ✅ 248 |
| `本案規範未收錄` | 對得到章節，但本案規範書沒收錄該章 | ✅ 188 |
| `請確認依據` | 沒有章節，或章節無相關準則 | ✅ 592 |
| `標單有，契約圖沒有` | 工項來源不一致 | ❌ 階段 2，無契約圖 |
| `請檢討使用何種工法` | 需選工法但找不到選了哪種 | ❌ 階段 4 |

多個條件同時成立時，沿用原 spec 的優先序概念，取最需要人介入的那一個。

### 3.3 依據分成「法規」與「標準」兩類

把規範書丟進既有的分析管線實測（18283 段，103 秒，成功完成）：抽出 2429 筆引用，
其中 **2263 筆（93%）是 `NOT_FOUND`**。

原因不是抽取壞掉，是**系統沒有標準的資料來源**。抽到的大半是 `CNS 2473`、
`CNS 8499`、`ASTM A307`、`AWS D1`，而 `taiwan_law` 只有法規，`pcces` 刻意拒絕
比對標準（見 `pcces_source.py` 開頭）。縮小到「相關準則」區塊也一樣：1408 筆裡 1146
筆是標準、262 筆不是（2026-10-07 實測：規則與字典兩層抽取，LLM 關閉）。

顯示「CNS 2473 — 查無此法規」會讓人以為規範引用了不存在的標準。事實是我們沒有
那個來源。所以依據分兩類：

| 類別 | 來源 | 處理 |
|---|---|---|
| **法規** | 章節 `1.4 相關準則` 裡的法律／規則 | 走既有 `taiwan_law` 查證，拿得到現行／已修正／已廢止 |
| **標準** | 抽取器判為 `RegulationType.STANDARD` 者 | **引述，不查證**。標明出自本案規範書第 N 章 |

#### 3.3.1 法規查證：只採完全同名，查不到就不宣稱

（2026-10-15 補。階段 3 出貨時這一節尚未接上，下面是接上時的設計依據。）

**模糊比對必須排除。** 把依據名稱丟給 `taiwan_law` 做模糊搜尋，實測候選是：

```
低電壓金屬閉鎖型配電箱檢驗法 → 商品檢驗法、民法、醫事檢驗師法
屋內線路裝置規則            → 中央空氣調節系統電表及線路裝置規則、電線經過鐵路裝置規則、兵籍規則
檢查辦法                    → 交通部會計檢查辦法、傳染病危險群及特定對象檢查辦法
```

一個 CNS 配電箱檢驗方法的最佳候選是**民法**。這正是 `pcces_source.py` 開頭描述、
整個專案一路在防的「有信心的錯」。

**所以只採完全同名。** 實測 96 個相異的非標準依據名稱裡，13 個在全國法規索引中
完全同名，涵蓋 **186 筆依據**，且**零誤判**——13 個全是真法規（職業安全衛生法、
勞動基準法、噪音管制法、用戶用電設備裝置規則、營建工程空氣污染防制設施管理辦法…）。

**查不到同名的標成「未查證」，不是「查無此法規」。** 這個區別是這一節的重點。
實測 `屋內線路裝置規則`（129 筆依據）與 `建築技術規則`（17 筆）都查不到，但原因不同，
而且兩個都不是「查無此法規」：

- `建築技術規則`是真的法規，只是不以那個名稱登錄在索引裡——索引中拆成建築構造編、
  建築設備編等四編。
- `屋內線路裝置規則`是**舊名稱**。2018-07-17 經濟部令把它更名為 `用戶用電設備裝置規則`
  （全國法規資料庫該法規沿革第 19 筆：「原名稱：屋內線路裝置規則；新名稱：用戶用電設備
  裝置規則」），索引只有新名稱（`J0030018`），沒有任何一筆名稱含「屋內線路」。本案規範書
  引用的是更名前的名稱，所以查不到——這是**對規範書的檢查發現**，不是索引缺資料。同一部
  法規以新名稱出現的 97 筆依據，就是上面 13 個同名裡的 `用戶用電設備裝置規則`。

| 狀態 | 意義 |
|---|---|
| `null` | **未查證**——沒有送查（標準），或查不到完全同名。系統不做任何宣稱 |
| `ACTIVE` / `AMENDED` / `REPEALED` | 完全同名查到了，沿用既有的 `RegulationStatus` |

**永遠不存 `NOT_FOUND`**：那個值的意思是「我們查過，這個法規不存在」，而我們的
依據來自規範書自己宣告的清單，沒有立場那樣宣稱。

**覆蓋率（實測，要寫進 `docs/api.md`）：** 792 筆非標準依據裡 186 筆（23%）拿得到
狀態；2054 筆標準依據一筆都不查（沒有 CNS 資料來源）；其餘 606 筆未查證。

查證在 `ChecklistService.build()` 抽完依據之後跑，**依相異名稱查一次**：送進來源的是
全部 96 個相異的非標準名稱，不是 792 筆依據各查一次。**13 是其中查得到完全同名的個數，
不是查詢次數**——沒查到的 83 個名稱同樣各花了一次查詢。`GET` 照樣只讀，不重查。

**成本（2026-10-16 實測，真實的 96 個名稱，`verify_names` 每次用全新的來源）：**
整批約 2–4 秒——最快一批 1.94 秒，一般 2.8–3.7 秒，機器負載高時曾超過 8 秒。這是
96 次全索引模糊比對（每次約 20–38 毫秒）加上冷載入索引（約 25 毫秒）。它在 `POST`
裡**同步**執行，沒有背景化，所以每次 `POST` 都要付這一段。這也解開了一個耗時之謎：
先前階段量到 `POST` 從這個分支之前的 2–4.6 秒變成之後的 6.4–8.6 秒，多出來的就是查證。
同一程序內、同一份資料、只切換是否查證的成對量測：不查證 1.93–4.79 秒、查證 3.64–8.10
秒，差額 1.55–3.33 秒，與 `POST` 內 `verify_names` 自己的耗時（1.65–3.52 秒）相符；
這台機器的速度本身會漂移約兩倍，所以絕對值對不上先前的量測，但每次多出來的就是這一段。

這也是為什麼**不走全文分析**：規範書的價值是「它說要依據什麼」，不是「它引用的
法規現不現行」。那條路不慢（103 秒可接受），但會把引述當成查證失敗。

## 4. 資料模型

新增兩張表。`documents` / `work_items` / `regulation_references` 語意都不改。

### `spec_chapters` — 本案施工規範的章節索引

| 欄位 | 說明 |
|---|---|
| `document_id` | 指向 role = `specification` 的那份文件 |
| `code` | `01725` |
| `title` | `施工測量` |
| `version` | `V3.0` |
| `first_page` / `last_page` | `61` / `63` |

一份規範書約 86 列。它是**對一份文件建的索引**，不是另一份真相——和 `work_items`
由標單建出來是同一個模式：有明確的 build 步驟，重跑取代。

### `work_item_bases` — 每個工項找到的依據

| 欄位 | 說明 |
|---|---|
| `work_item_id` | |
| `basis_type` | 沿用既有的 `RegulationType`（`enums.py`）。`STANDARD` 的定義本來就是「CNS / ISO / ASTM / JIS 等標準」，分類交給既有抽取器的輸出，不另外發明規則 |
| `reference` | `噪音管制法` ／ `CNS 2473` |
| `detail` | 出處，只寫到章：`第01725章 相關準則`。不寫小節號——相關準則不一定在 1.4（實測有 4 章在 1.3），系統不宣稱它不知道的小節號 |

**只存「找到的」。** 原 spec 的模型有 `found: 有沒有找到`，但不存 `found=false`
的列——「沒找到」有三種原因，而三種**全部算得出來**：

| 情況 | 怎麼算 |
|---|---|
| 沒有章節 | `work_item.cost_code` 為空，或查不到 PCCES 章節 |
| 本案規範未收錄 | 有章節，但 `spec_chapters` 沒有這個 code |
| 章節無相關準則 | 章節在，但沒有對應的 basis 列 |

存 `found=false` 要多存兩千多列，而且得連原因一起存——那違反原 spec 自己的規則：
**「狀態由資料算出來，不要存成可能過期的欄位」**。檢核結果同理，查詢時算。

## 5. 章節怎麼切

規範書每頁頁首是 `<組碼> <章碼>-<頁次> V<版本> <日期>`：

```
01725 01725-1 V3.0 2013/01/10     組碼與章碼相同
05500 05503-1 V5.0 2020/08/19     組碼與章碼不同 ← 要抓 05503
```

實測 772 頁裡 748 頁（97%）符合。**不要求 regex 完美**——沒有頁首的頁歸給前一頁
的章節（它們是延續頁，多半是跨頁大表）。這條規則比把 regex 調到 100% 穩健。

章節內文結構是 PCCES 標準的三段式：

```
1. 通則    1.1 本章概要  1.2 工作範圍  1.3 相關章節  1.4 相關準則 ← 依據在這
2. 產品    2.1 材料（CNS 標準多在這）
3. 執行    3.1 準備工作  3.2 施工方法
```

本案規範書不全照這個編號：有「相關準則」的 79 章裡，75 章編在 1.4，4 章（01523、01574、
02786、03110）編在 1.3，所以定位依據時比對的是 `1.<數字> 相關準則`，不寫死 1.4。

**`spec_chapters` 與 PCCES 目錄是兩個不同的東西**，不要混用：

- **PCCES 目錄**（`data/pcces_index.json`，315 章）→ 給章名。全國共通，階段 1 已在用。
- **`spec_chapters`**（本案 86 章）→ 給實際條文。每個專案不同，版本也不同。

兩者的落差就是 `本案規範未收錄`。

## 6. 元件切分

```
backend/app/
  specs/                        新套件，和 workitems/ 同一個模式
    chapter_reader.py           規範書 PDF → SpecChapterRow[]（章碼、章名、版本、頁範圍、內文）
    basis_reader.py             章節內文 → 相關準則／標準的原始字串；只做定位

  repositories/checklist.py     spec_chapters / work_item_bases
  services/checklist_service.py
      build_spec_index(project) 建章節索引
      build_bases(project)      逐工項建依據
      checklist(project)        組檢核表（檢核結果在這裡算）
```

資料流：

```
標單 ─────────→ work_items              （階段 1 已有）
規範書 ───────→ spec_chapters ──┐
                                ├──→ work_item_bases ──→ 檢核表
PCCES 目錄 ──(計價代碼)─────────┘            （結果用算的）
```

`chapter_reader` 直接讀 PDF 檔，不走 `document_sections`——和 `read_boq` 讀標單檔
一致。好處是章節索引**不依賴那份規範書有沒有跑過分析**，少一個時序耦合。

法規的正規化與查證交給既有的 `extractors` + `matching` + `sources`，不寫新的抽取器。

API 沿用專案既有的動詞：

- `POST /api/projects/{id}/checklist` — 建立（重跑取代）
- `GET /api/projects/{id}/checklist` — 查詢

## 7. 錯誤處理

**沒掛施工規範 → 不報錯，照樣產出檢核表。** 這裡刻意和階段 1 不對稱：
`build_work_items` 沒掛標單是 400，因為沒有標單就沒有工項、表是空的；沒有規範書
時**表還在**，1028 個工項都在，只是依據欄全是「請確認依據」。報錯會讓使用者什麼
都拿不到。這條不對稱要寫進程式碼註解，否則下一個人會當成漏寫。

**切不出任何章節 → 報錯。** 換一份頁首格式不同的規範書時會發生。照原 spec 第 8 節
對標單表頭的規則：「找不到表頭要報錯，不是產出空表」。安靜產出空索引的結果，是
一張全部「請確認依據」的表——看起來像「這個案子沒有依據」，實際是「我們沒讀懂
規範書」。

**規範書是 `DEGRADED` → 把警告帶進檢核表。** 規範書若有大量圖頁，章節內容可能
殘缺，檢核表頭要說明，不能讓人以為依據是完整的。（`13.施工規範.pdf` 實測是 `OK`，
0/772 圖頁。）

**重跑取代。** 換規範書時舊的 `spec_chapters` 與 `work_item_bases` 要清掉，
和 `replace_work_items` 同模式。

## 8. 測試策略

測試資料全部程式產生，不 commit binary fixture：`factories.py` 加
`make_spec_pdf_bytes(chapters=...)`，用 PyMuPDF 造一份有正確頁首格式的小規範書。

從實測挖出來的案例各要一個測試：

| 案例 | 為什麼 |
|---|---|
| 頁首 `05500 05503-1 V5.0` | 組碼≠章碼，要抓 05503 |
| 沒有頁首的延續頁 | 歸給前一章，不要丟掉（實測 24 頁） |
| 切出 0 章 | 要報錯 |
| 有章節但不在 `spec_chapters` | → `本案規範未收錄` |
| `CNS 2473` vs `噪音管制法` | 前者標準不查證，後者走 `taiwan_law` |
| 沒掛規範書 | 檢核表仍產出，全部「請確認依據」 |

**Golden set**（原 spec 第 9 節要求）：用程式產生的小規範書與小標單，三種檢核結果
各至少一筆。真實文件那組數字（**248 / 188 / 592**）寫在本文件第 2 節作為驗收基準，
人工驗一次——和階段 1 把 1028/438 寫進文件的作法一致。真實檔案在 repo 之外，
不能進測試。

## 10. 不做

沿用原 spec 第 3 節的排除項，另加：

- **不做契約逐工項比對**（第 3.1 節的理由）
- **不查證 CNS／ASTM 等標準**。系統沒有這個資料來源；要做是另一個題目
  （新增一個 standard source adapter），不在本階段
- **不做工法欄**（原 spec 第 7 節，屬階段 4，且需要契約圖）
- **不做前端檢核表畫面**。本階段只到 API，和階段 1 的作法一致（階段 1 的畫面是
  後來另外做的）。畫面要等 API 的形狀與回應大小確定之後再設計
