# 案例：引用可驗證的法規問答

> 檢索到的條文交給 Claude，回答必須逐字引用，再由程式比對原文驗證。保留測試集（20 題可回答＋9 題陷阱題）上：
> **錯誤答案 0 題**、陷阱題 **9/9 正確拒答**、模型給的引用 **100% 逐字出自原文**；
> 答對率由原本字詞搜尋的 **50% 提升到 75%**（另 10% 部分正確），差距幾乎全來自檢索。

程式：`backend/app/services/regulation_qa_service.py`、`backend/app/search/grounding.py`、
`backend/app/ai/anthropic_provider.py`（`answer_regulation_question`）、`POST /api/search/answer`、搜尋頁的「問 AI」。
評估：`scripts/eval_qa.py`、`data/qa_eval/`，完整數字在 [qa-eval-results.md](qa-eval-results.md)。
檢索這一段的設計與評估見 [semantic-search.md](semantic-search.md)。

---

## 1. 要防的是什麼

法規問答最怕的不是「答不出來」，而是**看起來很有把握的錯誤答案**：

- 引用一條不存在的條文，或條號對、內容是編的；
- 拿主題相近的條文硬答（問消防設備檢修頻率，拿建築物公共安全檢查的頻率來答）；
- 條文本身沒寫，模型用自己的知識補上，讀的人無從分辨哪句有依據。

監造和品管人員會照著答案去做，所以設計目標的順序是：**不能錯 > 可以查證 > 答得出來**。

## 2. 設計

```
問題 → 混合搜尋取前 8 條條文 → Claude 只根據這 8 條回答，逐字引用
     → 程式驗證每條引用 → 決定要不要顯示
```

**模型端（prompt `qa_v1`）**：只能根據提供的條文回答；每個規定都要附引用，引文從原文逐字複製；
條文不足就回 `answerable: false`，說明找到什麼、缺什麼。輸出用結構化輸出（JSON schema），不靠解析自由文字。
條文與問題都包在標籤裡，系統指令要求忽略其中的指示（使用者輸入與法規內容都視為資料）。

**程式端（`grounding.py`）**：不讓模型自己檢查自己，用字串比對：

| 檢查 | 擋下什麼 |
|---|---|
| 引的條文必須是這次提供的 8 條之一 | 引用不存在或沒給它的條文 |
| 引文正規化（全半形、空白）後必須是**那一條**原文的子字串 | 改寫、拼湊、張冠李戴（真的句子掛錯條） |
| 引文至少 6 個字 | 「雇主」「應」這種到處都對得上的短字串 |

**顯示規則**：至少一條引用通過才顯示回答，沒通過的引用照樣列出並標原因；
模型說有答案、但**沒有任何一條引用通過**，就不顯示回答，只列檢索到的條文。寧可少答，也不讓沒依據的答案出現在畫面上。

**選模型與成本**：Claude Opus 5.5，effort `medium`。開啟伺服器端 `fallbacks: "default"`：
安全分類器誤擋時由其他模型接手，實際回答的模型記在 AI 呼叫紀錄。每次呼叫連同 token 用量寫進 `ai_invocation_log`。
實測每題約 **US$0.03**、延遲中位數約 **7 秒**。

## 3. 評估方法

**題目**：
- 可回答 54 題：沿用搜尋評估集的關鍵字題與口語題（每題已標好正確條文）。
  指名條號的題目是在測搜尋，不是問句；只對到規範章節的題目沒有內文可答，這兩類不收。
- 無法回答 18 題（`data/qa_eval/unanswerable.json`）：答案在語料以外的法規。
  多數**刻意貼近語料主題**，例如消防安全設備檢修申報（語料只有公共安全檢查）、
  空污費費率（語料只有營建空污防制設施）、勞工健康檢查頻率（職安法只說「定期」）。

**開發集／保留測試集**沿用搜尋評估的劃分（陷阱題單數號為開發、雙數號為測試）。
開發集跑完沒有改 prompt；保留測試集只用來報數字。

**兩種檢索器對照**：同一題分別用混合搜尋和原本的字詞搜尋取條文，其他完全相同，看檢索品質對最終答案的影響。

**判定分兩層**：
1. 程式判定（決定性）：引用驗證與狀態判定，和上線同一套程式碼（`check_citations`、`decide`）。
2. LLM 裁判（Claude Opus 5.5，effort `high`）：只評「可回答且有回答」的題目。
   拿**正確條文全文**判斷結論對不對（correct／partial／incorrect），
   拿**被引用的條文**判斷回答裡有沒有條文沒寫的主張（faithful）。

**裁判本身也要驗證**：抽查 10 題隨機樣本加上所有被判 incorrect 或不忠實的 4 筆，逐一對照條文，
判斷全部同意。被判不忠實的都是模型在條文之外多推了一步，例如把「應明訂」寫成「應在契約中明訂」，
裁判抓得比人還嚴。**限制**：這次抽查是由 Claude（寫這份程式的同一個模型）做的，不是獨立的人工審查；
請領域專家看過一輪是下一步。

## 4. 結果

保留測試集（可回答 20 題、陷阱題 9 題）：

| 指標 | **混合搜尋** | 字詞搜尋（原本） |
|---|---:|---:|
| 正確 | **75%**（15） | 50%（10） |
| 部分正確 | 10%（2） | 20%（4） |
| **錯誤** | **0%** | **0%** |
| 說查不到（誤拒答） | 15%（3） | 30%（6） |
| 正確條文有在送給模型的 8 條裡 | 90% | 60% |
| 主張都有引用條文支持（faithful） | 100% | 100% |
| **陷阱題正確拒答** | **9/9** | **9/9** |
| 引用通過逐字驗證 | 92/92 | 86/86 |

開發集（34 題、陷阱 9 題）：混合搜尋正確 94%、部分正確 3%、錯誤 0%、誤拒答 3%；字詞搜尋正確 59%。

### 讀數字

1. **檢索決定上限。** 兩種檢索器用同一個模型、同一個 prompt，答對率差了 25～35 個百分點，
   和「正確條文有沒有送到模型手上」的差距幾乎一樣。開發集兩欄數字甚至完全相同（94% 對 94%、59% 對 59%）。
   要提升問答品質，先改檢索，不是先改 prompt。
2. **檢索失敗時，模型說「查不到」，不是瞎編。** 字詞搜尋找錯條文時，模型的反應是誤拒答（30～38%），
   不是錯誤答案。混合搜尋下 54 題可回答題，**0 題答錯**；
   4 題誤拒答中有 3 題是正確條文沒被檢索到，剩下 1 題（「技師簽名蓋章的設計圖要負什麼責任」）
   是問題本身問的是法律責任，條文只規定簽證義務，模型的拒答其實說得通，這題的標註可以再商榷。
3. **陷阱題全擋下。** 例如問消防設備檢修頻率，模型回答提供的條文只有公共安全檢查，
   不能拿來回答消防設備；問加班上限，模型指出條文只有高溫作業的特殊工時，不是一般延長工時。
4. **程式驗證沒有攔到任何東西，但仍然要有。** 兩份評估集、兩種檢索器下，Opus 5.5 一共給了 528 條引用，全部逐字出自原文，驗證一次都沒觸發。
   這是好消息，但不代表可以拿掉：換模型、換 prompt、換語料時，它是唯一不靠模型自律的防線。
   單元測試涵蓋了改寫、拼湊、掛錯條、引用沒提供的條文這幾種情況。
5. **部分正確的共同模式是漏掉補充規定。** 例如回答了採購法第 58 條的處理方式，
   卻漏了施行細則第 79 條「總標價偏低」的認定標準。這是檢索只取 8 條、母法與細則沒有一起出現造成的，
   下一步可以在檢索時把母法與它的施行細則綁在一起。

### 評估過程中修掉的 bug（透明起見）

- **結構化輸出的 schema 被 API 拒絕。** 巢狀物件也要標 `additionalProperties: false`，原本只處理最外層。
  這是既有的 bug：抽取功能的 schema 也有巢狀物件，只是過去一直沒有用真的 API 跑過。已改成遞迴處理，並加了測試。
- **條文數不足。** 原本先取前 8 名、再去掉規範章節，導致「施工日誌」這題前 8 名全是章節、一條條文都沒送出去。
  這是**在保留測試集上發現的**；修正後兩份評估集都重跑了，混合搜尋的數字完全沒變，字詞搜尋開發集多了 1 題答錯。
  上表是修正後的數字。
- 評估腳本一度把呼叫失敗寫進快取，也把失敗算成「正確拒答」；都已修正，失敗另外列一行。

## 5. 還沒做的

- **獨立的人工審查**：裁判抽查需要由懂法規的人做一輪，評估集標註也一樣。
- **母法與施行細則一起檢索**（見上面第 5 點）。
- **規範章節的內文**：目前只有章名，問「混凝土澆置後怎麼養護」只能指出章名，無法回答內容。
- **多輪追問、使用者文件**：目前只回答單一問題，只查法規條文，不查上傳的工程文件。
- **成本**：每題 US$0.03 對內部工具可以接受；量大時可以試 effort `low` 或改用 Sonnet，評估腳本可以直接比較。

## 6. 重現

```bash
pip install -r requirements-semantic.txt
python scripts/eval_qa.py --sets dev test --dry-run          # 估算費用，不呼叫 API（約 US$12）
python scripts/eval_qa.py --sets dev test --write docs/qa-eval-results.md
```

需要 `.env` 的 `ANTHROPIC_API_KEY`。模型回應快取在 `data/generated/qa_cache/`，
重算指標或改報表格式不必再付費；改了 prompt、模型或檢索，快取的鍵會變，自然會重新呼叫。
這次開發加評估（含試跑與修正後重跑）實際花費不到 US$10。
